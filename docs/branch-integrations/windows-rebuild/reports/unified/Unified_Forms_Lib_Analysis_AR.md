# التقرير الموحد لتحليل Oracle Forms وربطه بالمكتبات والملفات السابقة

**النطاق:** `Forms.zip` + `Lib.zip` + ملفات FMX السابقة في `مجلد١.zip`  
**التاريخ:** 11 سبتمبر 2026  
**المؤلف:** Manus AI

## 1. الحكم التنفيذي

تم تحليل أرشيف `Forms.zip` بالكامل على مستوى الملفات الثنائية والسلاسل والاعتماديات، ثم ربطه بمكتبات `Lib.zip` وملفات Forms التي أُرسلت سابقًا. يحتوي `Forms.zip` على **1,490 ملف FMX** بإجمالي **584,550,828 بايت**، إضافة إلى 13 ملف RDF، وملفات سجل وتشخيص وملف PLX.

استخراج السلاسل نتج عنه **1,573,200 سلسلة**، و**162,092 مؤشرًا يشبه SQL**، و**41,497 اسمًا يشبه الدوال أو الحزم**، و**8,902 مؤشر Trigger**، و**2,396 مرجع مكتبة**، و**771 مرجع نافذة**. هذه النتائج لا تعني عددًا دقيقًا للتنفيذات؛ لأن FMX ملف مجمع ويكرر الأسماء داخل بيانات Forms الوصفية والتنفيذية.

النتيجة الأهم هي أن النظام ليس مجموعة شاشات مستقلة. معظم النوافذ تعمل داخل هيكل موحد يعتمد على:

```text
YSERP_MNU
  → YSERP_LIB / LYSERP_LIB
    → IAS_*_PKG وYS_*_PKG وGEN_PKG
      → Forms DML وTriggers وLOV وPost/Commit
        → Oracle Tables / Views / Packages
          → GL / AR / AP / Inventory / HR / POS / MRP
```

وتوجد طبقة ثانية عالية الحساسية هي طبقة العميل المحلي: `YSERP_SYS.dll`, `YSComUsb.dll`, `d2kwut60.dll`, `YsGoogleMap.ocx`, `TransferToMTN.exe`, `Excel.exe`، إضافة إلى Oracle Forms Runtime 32-bit.

## 2. نطاق التحليل وحدوده

تم فك الأرشيف في مساحة معزولة، وحساب أحجام وبصمات الملفات، وقراءة الملفات الثنائية دون تشغيلها. تم استخراج ASCII وUTF-16LE، ثم تصنيف النتائج إلى أسماء نوافذ، مكتبات، إجراءات، Triggers، SQL-like، جداول، مراجع ملفات، وتكاملات Windows.

لم يتم الاتصال بقاعدة البيانات، ولم يتم تشغيل Forms Runtime، ولم يتم تنفيذ DLL أو OCX أو EXE. ولذلك يمكن إثبات وجود اسم أو مرجع أو استعلام مخزن داخل الملف، لكن لا يمكن إثبات سلوك كل Trigger في كل حالة استثنائية دون ملفات المصدر `FMB/PLL` أو تشغيل بيئة اختبار.

الكتالوج الكامل للسلاسل محفوظ في ملف مضغوط، والكتالوج البنيوي لكل Form محفوظ في JSON. وهما يمثلان طبقة الأدلة التي بني عليها هذا التقرير.

## 4. طبقة Forms المشتركة

تكرر أكثر من ألف Form نمطًا موحدًا من الوظائف. الأسماء الأكثر تكرارًا هي `GEN_PKG`, `IAS_USR_PKG`, `EXIT_PROC`, `PRE_FORM_PRC`, `PRINT_PROC`, `FILL_ALL_LIST_PRC`, `IAS_GET_ENC_PASS_FNC`, `SYS_SCREEN`, `YSERP_MNU`, `LOV_TRG`, `YSERP_LIB`, `KEY_LISTVAL_PRC`, `LOV_PKG`, `LIST_PROC`, `UPDATE_PROC`, `POST_FORMS_COMMIT_PRC`, `WHEN_NEW_FORM_INSTANCE_PRC`, و`WHEN_TIMER_EXPIRED_PRC`.

هذا النمط يوضح دورة الشاشة التالية:

1. **تهيئة الشاشة:** `PRE_FORM_PRC` و`WHEN_NEW_FORM_INSTANCE_PRC` يقرآن الفرع والسنة والشركة والمستخدم والمعلمات.
2. **ضبط القائمة:** `YSERP_MNU` و`SYS_SCREEN` يحددان النظام والشاشة والصلاحيات.
3. **تحميل القوائم:** `LOV_PKG`, `LOV_TRG`, `FILL_ALL_LIST_PRC`، وقوائم اختيار من المخزن والصنف والعملة والحساب ومركز التكلفة.
4. **إضافة السجل:** `ADD_PROC` أو وظيفة مجال مشابهة.
5. **التحقق السابق للحفظ:** `B4SAVE_PRC`, `CHK_B4SAVE_MST_PRC`, `CHK_B4SAVE_DTL_PRC`.
6. **الحفظ والتعديل:** `SAVE_PROC`, `UPDATE_PROC`، وربط تفاصيل الرأس.
7. **الترحيل:** `POST_FORMS_COMMIT_PRC` أو `IAS_POSTING_*`.
8. **الحذف أو الإلغاء:** `DELETE_PROC`, `CHECK_DOC_DEL_PRC`، مع فحص الترحيل والمردود والارتباطات.
9. **الطباعة والتصدير:** `PRINT_PROC`, `REP_FORM`, `Excel.exe`, و`IMP_F_EXCEL_PRC`.
10. **المراقبة:** Timer وAudit وSession وخصائص النظام المحلي.

هذه البنية تعني أن تحويل شاشة واحدة إلى React لا يكفي. يجب تحويل **قالب Forms المشترك** إلى خدمات خلفية موحدة للصلاحيات، والـLOV، والتدقيق، والتسلسل، والحفظ، والترحيل، والتقارير.

## 6. مسار الذمم المدينة AR

### 6.1 `ARST004.fmx`: فاتورة البيع والحركة المرتبطة

هذه من أكثر شاشات AR تعقيدًا، إذ تحتوي على **8,491 سلسلة** و**659 مؤشر SQL** و**98 اسم إجراء** و**12 Trigger**. وترتبط بـ`YSERP_LIB`, `YSERP_MNU`, `ERP_CODE_TRNS`, `GLST004`, `INV_ITM_TRNS`, `YS_ICODE_LOV`, و`TransferToMTN.exe`.

الجداول الواضحة من الاستعلامات تشمل:

- `IAS_BILL_MST` و`IAS_BILL_DTL` لرأس وتفاصيل الفاتورة.
- `IAS_BILL_MST_ADD_DISC` و`IAS_BILL_DTL_ADD_DISC` للخصومات الإضافية.
- `IAS_RT_BILL_MST` و`IAS_RT_BILL_DTL` للمردود.
- `ITEM_MOVEMENT` للحركة المخزنية الناتجة عن الفاتورة.
- `VOUCHER_DETAIL` و`MASTER_OUT_BILLS` و`IAS_OUTGOING_MST` للارتباط المالي والتشغيلي.
- `SALES_ORDER`, `QUOTATION`, `IAS_RESERVE_DTL`, و`IAS_ITM_ATTACH_OTHRS` للطلبات والحجز والمرفقات.
- `IAS_WHTRNS_MST`, `IAS_WORK_ORDER_MST`, و`MNT_WORK_MST` لروابط الحركات الأخرى.

الدوال الأساسية هي `ADD_PROC`, `SAVE_PROC`, `UPDATE_PROC`, `DELETE_PROC`, `B4SAVE_PRC`, `CHK_B4SAVE_MST_PRC`, `CHK_B4SAVE_DTL_PRC`, `CHECK_DOC_DEL_PRC`, `IAS_INSRT_OUT_BILLS_PKG`, `IAS_POST_IN_SAV_PKG`, `IAS_INSTALLMENT_AR_PKG`, `IAS_GL_LMT_PKG`, `IAS_SALESMAN_PKG`, و`IAS_TRNS_PKG`.

القراءة الوظيفية لدورة الفاتورة هي:

```text
اختيار العميل والعملة والسعر والمخزن
  → اختيار الصنف والوحدة والدفعة/التاريخ
  → فحص السعر والخصم والحد الائتماني والصلاحيات
  → حفظ الرأس والتفاصيل
  → تحديث الطلب أو الحجز أو أمر العمل
  → إنشاء أو تحديث حركة المخزون
  → إنشاء الحركة المالية أو القيد
  → طباعة أو تصدير الفاتورة
```

يظهر في الكود إلغاء ارتباطات عند حذف أو تعديل الفاتورة، مثل إعادة `PROCESSED=0` للطلب أو العرض أو الحركة أو أمر العمل. لذلك لا يجوز تحويل الحذف إلى `DELETE` مباشر في API. يجب استخدام حالات `DRAFT`, `POSTED`, `REVERSED`, و`VOIDED` مع خدمة عكس محاسبي ومخزني.

### 6.2 `ARST006.fmx`: مردود البيع

تحتوي على **5,589 سلسلة** و**465 مؤشر SQL** و**79 اسم إجراء** و**11 Trigger**. ترتبط بـ`IAS_RT_BILL_MST`, `IAS_RT_BILL_DTL`, `IAS_RT_BILL_MST_RQ`, `ITEM_MOVEMENT`, `GR_DETAIL`, و`IAS_WCODE_PKG`.

النتيجة المحاسبية ليست مجرد فاتورة سالبة. المردود يمكن أن يعكس حركة مخزون، ويعدل دفعة أو رصيدًا، ويؤثر على ضريبة أو قيد أو دفعة أو مستند مرتبط. يجب تنفيذ المردود في Transaction واحدة أو عبر Outbox موثوق مع Idempotency.

## 7. مسار المشتريات AP

### 7.1 `APST005.fmx`: فاتورة الشراء

تحتوي على **6,688 سلسلة** و**438 مؤشر SQL** و**76 اسم إجراء** و**12 Trigger**. ترتبط بـ`IAS_PI_BILL_MST`, `IAS_PI_BILL_DTL`, `P_ORDER`, `GRN_MASTER`, `GR_NOTE`, `IAS_CHECK_INCM_MST`, `ITEM_MOVEMENT`, `IAS_PRICING_LEVELS`, `IAS_PRIV_AP`, و`IAS_PRIV_PRICE`.

تتحقق الشاشة من:

- مستوى السعر الافتراضي.
- ارتباط فاتورة الشراء بأمر الشراء والاستلام.
- الكمية المستلمة مقابل الكمية المفوترة.
- التسلسل والدفعة وتاريخ الانتهاء.
- المخزن ومركز التكلفة والمشروع والنشاط.
- صلاحية المستخدم على المورد ومدير المشتريات والأسعار.

عند التعديل أو الحذف تعيد فتح حالة أمر الشراء أو الاستلام عبر تحديث `P_ORDER`, `GRN_MASTER`, و`IAS_CHECK_INCM_MST`. لذلك يجب اعتبار فاتورة AP Aggregate محاسبيًا ومخزنيًا، لا شاشة CRUD.

### 7.2 `APST003.fmx` و`APST015.fmx`

`APST003` شاشة تشغيلية كبيرة نسبيًا تحتوي على **334 مؤشر SQL** و**66 اسم إجراء**. وهي جزء من دورة الشراء المرتبطة بالصنف والمورد والمخزن.

أما `APST015` فهي شاشة الطلب الآلي التي حُللت في التقرير السابق. وجودها الآن ضمن 1,490 Form يؤكد أن `Lib.zip` كان يحتوي على نسخة تشغيلية من مكتبة ونوافذ مساندة، بينما `Forms.zip` يقدم مجموعة النوافذ الكاملة وربطها بالقائمة العامة.

## 8. الأستاذ العام والمالية

### 8.1 `GLST001.fmx` و`GLST002.fmx`

تحتوي `GLST001` على **364 مؤشر SQL** و**77 اسم إجراء**، وتحتوي `GLST002` على **346 مؤشر SQL** و**71 اسم إجراء**. كلاهما يعتمد على `YSERP_LIB`, `IAS_GEN_PKG`, `IAS_USR_PKG`, `IAS_POSTING_PKG`، ونوافذ مثل `ADMT030`, `ERP_CODE_TRNS`, `ARST004`, و`APST005`.

هذا يوضح أن GL لا يعمل بمعزل عن AR وAP والمخزون. القيود والصلاحيات والأرقام المرجعية تعبر بين المجالات، وأي ترحيل يجب أن يحافظ على:

- رقم المستند والسنة والفرع والشركة.
- العملة وسعر الصرف.
- الحساب ومركز التكلفة والمشروع والنشاط.
- حالة التدقيق والاعتماد والترحيل.
- عكس القيد عند الإلغاء بدل حذف السجلات المرحلة.

### 8.2 `FAST089.fmx` و`FASDBA.fmx`

`FAST089` يحتوي على عدد مرتفع من Triggers ومؤشرات SQL ديناميكي ومؤشرات استثناء. `FASDBA` و`SHPDBA` يحتويان على أسماء حزم إنشاء جداول وفهارس وViews وTriggers، مثل `FAS_TABLE_PKG`, `FAS_VIEW_PKG`, `FAS_TRIGGER_PKG`, `SHP_TABLE_PKG`, و`GLS_VIEW_PKG`.

هذه ليست شاشات مستخدم عادية؛ إنها أدوات DBA أو Upgrade. يجب عزلها عن المستخدم النهائي، وتشغيلها فقط ضمن Migration Pipeline مراجع وموقّع، وليس من خلال Web UI متصل مباشرة بالإنتاج.

## 10. MRP والخزينة

يضم المجال 201 Form. أكبر شاشة هي `MRPACS004.fmx` بحوالي **12,581 مؤشر SQL**، وهي مرشح أول للمراجعة المنفصلة لأنها قد تحتوي SQL مولدًا أو بيانات إعداد وتهيئة كبيرة. `MRPSFC025.fmx` موجود في Forms ويرتبط بما ظهر سابقًا في `MRPDBA.plx`.

## 11. الموارد البشرية

تضم HR **207 Form**، وتظهر فيها `HRSLIB`, `HRS_GNR_PKG`, مصمم التقرير `HRSS031`, النماذج الطبية، الحضور، التقييم، الرواتب، الوثائق، والقروض أو السلف.

تتكرر إجراءات `HRS_INSRT_DATA_PKG`, `HRS_INSRT_FORM_DTL_PKG`, `HRS_POSTING_PKG`, و`HRS_*_PKG`. وبما أن بعض Forms تستخدم صيغًا وتقارير ديناميكية، يجب تطبيق قاموس حقول وصلاحيات Row-Level Security وعدم السماح بإدخال SQL أو PL/SQL حر من الواجهة.

## 12. الإدارة والتحديث

### 12.1 `ERP_Update_New_Version6.fmx`

هذه من أكبر الملفات من حيث السلاسل، وتحتوي على **24,543 مؤشر SQL** و**94 Trigger**. وجودها يدل على أن النظام يوزع أو يطبق تحديثات إصدار من داخل Forms. يجب اعتبارها أداة Deployment حساسة، وليس Form تشغيليًا.

### 12.2 `ERP_DBA_Cmp.fmx` و`ERP_DBA_DFLT_DATA*`

`ERP_DBA_Cmp` تحتوي على آلاف مؤشرات SQL، بينما نسخ `ERP_DBA_DFLT_DATA`, `ERP_DBA_DFLT_DATA_TRK`, `ERP_DBA_DFLT_DATA_LNG`, و`ERP_DBA_DFLT_DATA_LNG_TURKEY` تحتوي على إدخالات بيانات وقواميس وصلاحيات ولغات وحزم إنشاء مكونات المجال.

وجود نسخ `TRK`, `LNG`, و`TURKEY` يثبت تعدد نسخ البيانات أو مسارات التوطين والاختبار. يجب مقارنتها على مستوى DDL وDML قبل اعتماد أي نسخة كمرجع.

## 14. سجل التشغيل والتوافق

توضح السجلات أن البيئة التاريخية استخدمت:

- Oracle Forms Runtime **8.0.6.3.0**.
- Oracle TNS 32-bit.
- Windows NT/Windows 7-era runtime.
- SID باسم `ORCL` في السجلات المنقحة.
- اتصال TCP على المنفذ 1521 في بعض المحاولات.
- أخطاء `TNS-12203`, `TNS-12543`, `TNS-12535`, و`TNS-00513`.
- أعطال `ACCESS_VIOLATION` داخل `ifrun60.EXE` أثناء `EXIT_FORM` في `ERP_LOGIN`.

المعنى التشغيلي هو أن مشكلة النظام التاريخية ليست SQL فقط. هناك مخاطر توافق Runtime و32-bit وTNS وملفات مشاركة ومسارات Windows، ولذلك يجب تنفيذ مرحلة تثبيت بيئة Legacy قبل مقارنة النتائج مع النظام الجديد.

## 16. خطة تحويل عملية إلى React/Next.js مع الحفاظ على Oracle

### المرحلة الأولى: تثبيت المصدر

يجب حفظ Oracle كـSystem of Record، وإضافة API Read-Only أولًا. يتم إنشاء قاموس `FORM → DOMAIN → TABLES → PACKAGES → PERMISSIONS` من JSON والكتالوجات، ثم مراجعته مع DBA ومالك المجال.

### المرحلة الثانية: الخدمات المشتركة

يجب بناء خدمات موحدة لـ:

- الهوية وRBAC وRow-Level Security.
- الفرع والسنة والشركة والمستخدم.
- LOV والبحث والترجمة.
- التسلسل والوثائق.
- التدقيق والمرفقات.
- حالات المستند والتعليق والاعتماد.
- الترحيل والـOutbox وIdempotency.
- الطباعة والتقارير.

### المرحلة الثالثة: القراءة ثم الكتابة

يبدأ التحويل بتقارير AR/GL وقراءة المخزون، ثم شاشات إعداد منخفضة المخاطر، ثم طلبات الشراء، ثم الفواتير والمردود، ثم POS والترحيل. كل شاشة جديدة تعمل بجانب Forms وتُقارن نتائجها مع Oracle.

### المرحلة الرابعة: الترحيل والاعتماد

لا يتم حذف أو تعديل سجل مرحلة مباشرة من React. يتم إنشاء أمر عكس أو مستند إلغاء، وتُسجل هوية المستخدم والوقت والسبب والمرجع الأصلي. وتنفذ عمليات AR وAP وGL وInventory داخل Transaction منضبطة أو Saga محاسبية مع مطابقة يومية.

## 17. الملفات المطلوب طلبها لاستكمال «كل سطر مصدر»

التحليل الحالي شامل للملفات المجمعة، لكنه ليس تفكيكًا كاملًا لـPL/SQL الأصلي. للوصول إلى كل Trigger وكل سطر يجب الحصول على:

- `FMB` المصدر لكل Form.
- `PLL` و`PLX` المصدرية أو ملفات `PKS/PKB` للحزم.
- DDL للجداول والقيود والفهارس والـViews والـTriggers.
- `RDF/REP` مع مصادر التقارير.
- ملفات `MMX` المصدرية و`SYSTEM.MMX`.
- `formsweb.cfg`, `tnsnames.ora`, وإصدار Forms/Oracle بعد حجب الأسرار.
- قائمة التشغيل الفعلية للـDLL وOCX وEXE.
- بيانات اختبار منزوعة الحساسية.

## 18. الخلاصة

أثبت الربط بين الأرشيفات أن `Forms.zip` هو طبقة الواجهة والتدفقات التفصيلية، وأن `Lib.zip` هو طبقة المكتبات والتكاملات المشتركة، بينما تكشف ملفات FMX السابقة عن نقاط الدخول والأمن والإقفال وPOS والـAR الأساسية.

النظام يحتوي على شبكة مترابطة من AR وAP وGL والمخزون وHR وPOS وMRP. أكثر نقطة حساسة في التحويل هي أن شاشة الفاتورة الواحدة تعدل أكثر من مجال: المستند، المخزون، الطلب أو الاستلام، الحسابات، الحد الائتماني، التدقيق، وربما الضريبة أو التأمين. لذلك يجب تحويل المنطق إلى خدمات مجال واختبارات مطابقة، وليس إلى نسخ حرفي لعناصر Forms داخل React.
