# العمليات الذرية لكل نافذة

## المبدأ

كل عملية تنفذها نافذة Forms تمثل **معاملة ذرية**. يجب أن تنجح العملية كاملة أو لا يظهر أي أثر دائم لها.

> لا يوجد حفظ جزئي لفاتورة أو قيد أو حركة مخزون. عند فشل أي خطوة، يتم التراجع عن كل تغييرات العملية الحالية.

## حدود المعاملة

```text
Window Trigger
  → Window Service Package
    → Validation
    → Document changes
    → Subledger changes
    → Inventory/AR/AP changes
    → GL journal
    → Audit event
    → Outbox event
  → COMMIT مرة واحدة عند النجاح
```

لا تنفذ الحزم `COMMIT` أو `ROLLBACK` من داخلها. صاحب المعاملة هو Trigger/Service boundary الذي بدأ العملية.

## قواعد إلزامية

| القاعدة | التطبيق |
|---|---|
| نجاح كامل أو فشل كامل | `SAVEPOINT` في بداية العملية و`ROLLBACK TO SAVEPOINT` عند خطأ قابل للمعالجة |
| عدم وجود Commit مخفي | ممنوع `COMMIT` داخل Package Body أو Trigger فرعي |
| منع التكرار | `IDEMPOTENCY_KEY` فريد لكل طلب حفظ/ترحيل |
| قفل المستند | `SELECT ... FOR UPDATE` قبل التعديل أو الترحيل |
| منع تعديل المرحل | Trigger قاعدة البيانات يمنع تحديث أو حذف `POSTED/REVERSED` |
| توازن القيد | فحص مجموع المدين والدائن قبل Commit |
| التدقيق ضمن المعاملة | Audit row يلتزم أو يتراجع مع العملية |
| Outbox ضمن المعاملة | يسجل الحدث قبل Commit ولا ينشر خارجيًا قبل نجاح Commit |
| العكس بدل الحذف | المستند المرحل يعكس بقيد جديد ولا يحذف |
| حدود النافذة | كل نافذة تستدعي API خاصًا بها، ولا تتشارك حالة معاملات عامة غير معزولة |

## دورة الحالات

```text
DRAFT
  → PENDING_APPROVAL
  → APPROVED
  → POSTED
  → REVERSED
```

أي فشل قبل Commit يعيد المعاملة إلى الحالة السابقة. لا يتم تحويل الحالة إلى `POSTED` قبل اكتمال AR/Inventory/GL/Audit.

## معالجة أخطاء Forms

يجب أن يستدعي Trigger طبقة API، ثم ينفذ `COMMIT_FORM` مرة واحدة فقط عند النجاح. عند الاستثناء، تستخدم Forms `ROLLBACK` أو `CLEAR_FORM(NO_VALIDATE)` بحسب حالة الشاشة، ثم تعرض رسالة آمنة للمستخدم.

## العزل

كل طلب يحمل `REQUEST_ID` و`IDEMPOTENCY_KEY`. لا يجوز إعادة استخدام نفس المفتاح لعمليتين مختلفتين. تستعمل الأقفال على مستوى الصفوف، مع ترتيب ثابت للأقفال لتقليل Deadlocks.

## الاختبار

لكل نافذة يجب اختبار فشل كل مرحلة على حدة والتأكد من أن عدد الصفوف والأرصدة يعود إلى ما قبل العملية. تشمل الاختبارات الحفظ، التعديل، الترحيل، العكس، فشل الشبكة، تكرار الطلب، وفشل قيد GL.
