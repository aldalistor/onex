# المرحلة الثالثة — ربط النوافذ بعقود قاعدة البيانات

## ما تم تنفيذه

أضيف عقد tRPC جديد باسم `windows.records` للبحث عن سجلات النافذة. يدعم العقد حاليًا نافذة `ARST004`، ويبحث في جدول `invoices` عن طريق رقم المستند أو الحالة، مع ترتيب السجلات الأحدث أولًا وحد أقصى قابل للتحديد.

تم ربط `WindowWorkbench` بالعقود التالية:

| العقد | الوظيفة |
|---|---|
| `windows.list` | تحديث فهرس النوافذ عند البحث |
| `windows.contract` | تحميل عقد النافذة ومصادره ووحدات التشغيل |
| `windows.records` | البحث الفعلي في سجلات النافذة |
| `masterData` | تحميل العملاء والمستودعات والأصناف |
| `invoices.create` | حفظ مسودة فاتورة فعلية |

عند فتح `ARST004`، يقرأ التطبيق بيانات العملاء والمستودعات والأصناف من قاعدة البيانات عند تفعيل `ONEX_USE_DATABASE=1`، ثم ينفذ الحفظ عبر معاملة `invoices.create`. المعاملة تنشئ رأس الفاتورة وتفاصيلها وسجل التدقيق. عند عدم توفر الاتصال، يعمل التطبيق في وضع fallback المحلي الآمن الموجود سابقًا.

## ضمانات الحفظ

يستخدم الحفظ مفتاح idempotency مبنيًا على `ARST004` ورقم المستند، ويمنع التكرار. الترحيل اللاحق الموجود في النظام يراجع المخزون، ويسجل حركة المخزون، وينشئ القيود، ويسجل التدقيق داخل معاملة واحدة عند استخدام قاعدة البيانات.

## حدود المرحلة

لم تتم إضافة جداول عامة وهمية لتمثيل 1,498 نافذة. بدلًا من ذلك، تم ربط أول نافذة تشغيلية كاملة بكياناتها الموجودة فعليًا. الخطوة التالية هي توسيع خريطة `legacyForm -> entity contract` إلى العملاء والأصناف والموردين والقيود والحركات والتقارير، مع عقود تحقق خاصة بكل وحدة.

## التحقق

نجح فحص TypeScript. نجحت اختبارات المشروع وعددها 16 اختبارًا. اكتمل بناء الإنتاج. تحذير حجم الحزم صادر من Mermaid الموجود سابقًا ولا يمثل فشلًا في المرحلة الثالثة.
