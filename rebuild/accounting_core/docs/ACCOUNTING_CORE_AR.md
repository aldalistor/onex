# نواة ONEX المحاسبية وربط النوافذ الأصلية

## الهدف

النواة الجديدة لا تستبدل أسماء Forms الأصلية. بل توفر طبقة محاسبية مركزية تحفظ هوية النافذة القديمة وتربطها بقدرة محاسبية واضحة. كل نافذة تدخل النظام من خلال Compatibility Layer، بينما تظل قواعد الترحيل والتدقيق والذرية في حزم ONEX المركزية.

## المجالات

| المجال | نواة ONEX | أمثلة نوافذ قديمة |
|---|---|---|
| AR | العملاء، الفواتير، الاستحقاقات، التحصيل، العكس | ARST004, ARST006, ARST023 |
| AP | الموردون، الشراء، الالتزامات | APST003, APST005 |
| GL | القيود، الحسابات، الفترات، الإقفال | GLST001, GLST002 |
| Inventory | الأصناف، المخزون، الحركات، التكلفة | INVT*, MTX* |
| POS | البيع والدفع والمردود | POST001, POS_INSTALL |
| التدقيق | أحداث غير قابلة للحذف ومنظومة Outbox | كل النوافذ |

## الذرية

كل عملية تبدأ بـ `ONEX_ATOMIC_API.begin_window`، وتستخدم Savepoint، وقفل الصف، ومفتاح Idempotency. لا تنفذ الحزم Commit داخليًا. يتم Commit مرة واحدة على حدود العملية بعد نجاح التحقق والترحيل والتدقيق.

## التوافق مع قاعدة Oracle القديمة

في المرحلة الأولى توجد جداول ONEX إلى جانب قاعدة IAS القديمة. لا يتم تعديل جداول IAS مباشرة من النواة قبل تعريف Mapping موثق ومختبر. بعد مقارنة النتائج، يمكن أن تستدعي طبقة التوافق حزم IAS الأصلية ذات التوقيع المؤكد بدل تكرار منطقها.

## النوافذ

ملف `database/02_register_legacy_windows.sql` يسجل جميع النوافذ البالغ عددها 1,490 نافذة. التسجيل لا يعني أن نافذة معينة أصبحت جاهزة للإنتاج؛ الحالة تبدأ `SPEC_ONLY` وتنتقل إلى `GOLDEN_MASTER_VERIFIED` بعد اختبارات القراءة والحفظ والترحيل والعكس.
